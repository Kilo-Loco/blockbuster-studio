# General-Purpose Stable-Diffusion-Ecosystem Web UIs: SwarmUI, InvokeAI, Fooocus/Forks, SD.Next

Research date: 2026-09-24. All star counts, license fields, and commit dates pulled live via `gh api` (GitHub REST API) on 2026-09-24 unless otherwise cited.

## SwarmUI (mcmonkeyprojects/SwarmUI)

### Takeaway
SwarmUI is MIT-licensed, actively developed (commits within the last day), has a documented first-class REST/WebSocket API separate from its UI, and already supports Wan 2.2 video plus FLUX and Qwen-Image — making it the strongest technical/licensing candidate of the four for a resold, self-hosted product, though it is a small, largely single-maintainer project (backed by a ComfyUI dependency) and its UI leans "power-user tool" rather than polished SaaS-studio.

### Cited Findings
- Repo: [github.com/mcmonkeyprojects/SwarmUI](https://github.com/mcmonkeyprojects/SwarmUI) — 4,597 stars, 458 forks, 149 open issues (live `gh api` pull, 2026-09-24).
- License: **MIT** (SPDX `MIT`, "MIT License") per live repo metadata — a permissive license with no copyleft or non-commercial restrictions, safe for reselling/hosting as a commercial product. — [repo license field](https://github.com/mcmonkeyprojects/SwarmUI)
- Last commit: 2026-09-23T10:15:13Z ("don't mispropagate errors"), with multiple commits per day in the days prior (e.g., multi-user role support, upscale/alpha handling) — very active, near-daily cadence. — [commits API](https://github.com/mcmonkeyprojects/SwarmUI/commits)
- Description: "A Modular Stable Diffusion Web-User-Interface, with an emphasis on making powertools easily accessible, high performance, and extensibility" — built on top of ComfyUI as its execution backend. — [GitHub repo](https://github.com/mcmonkeyprojects/SwarmUI)
- Tech stack: primarily C# (2.1M+ bytes, ASP.NET-style backend/server) with JavaScript (1.3M) and Python (200K, for the bundled/managed ComfyUI backend), plus HTML/CSS front end. — [languages API](https://github.com/mcmonkeyprojects/SwarmUI)
- API: SwarmUI exposes "a full-capability network API that you can use from external programs, both to use Swarm features (eg generate images) and to manage the Swarm instance (eg modify backends)." Most routes are POST + JSON; routes suffixed `WS` are WebSocket for streaming progress/previews (e.g., `GenerateText2ImageWS`). Documented in-repo at `docs/API.md` and `docs/APIRoutes/BackendAPI.md`. — [SwarmUI API.md](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/API.md), [BackendAPI.md](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/APIRoutes/BackendAPI.md)
- Wan 2.2 video: SwarmUI has full text-to-video and image-to-video support for Wan 2.2, including a "Video End Image" input to set the final frame, and community reports of ~81 frames/16fps in under 3 minutes on an RTX 3090 with lightx2v LoRAs. — [SwarmUI Discussion #716](https://github.com/mcmonkeyprojects/SwarmUI/discussions/716), [Civitai article](https://civitai.com/articles/17918/my-swarmui-fast-wan-22-image2video-with-lightx2v-setup-experimental)
- Modern image models: SwarmUI supports Stable Diffusion, FLUX (Dev, Krea, SRPO variants), Qwen-Image and Qwen-Image-Edit-Plus, Z-Image, and video models including Wan and Hunyuan Video. — [SwarmUI site](https://swarmui.net/) (via search aggregation)
- UI quality: dual-mode UI — a simple linear "Generate" tab for daily use plus a full ComfyUI node-graph "Comfy Workflow" tab for advanced pipelines; recent releases modernized the built-in model-downloader UI with "10x improved app performance." Framed by reviewers as a more usable layer over ComfyUI/A1111-style tools rather than a from-scratch consumer-studio design. — [SwarmUI "Why Use Swarm"](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/Why%20Use%20Swarm.md), [Civitai transition guide](https://civitai.com/articles/6024/using-a1111-why-not-swarmui-a-transition-guide)
- Maintainer risk: GitHub lists 30+ contributors on the repo (API caps listing at 30, actual count could be higher), but the project is driven predominantly by a single lead maintainer ("mcmonkey4eva") with no known corporate backing or funding round found in this research. — [contributors API](https://github.com/mcmonkeyprojects/SwarmUI/contributors)

### Inferences
- Because SwarmUI wraps ComfyUI as its execution engine rather than reimplementing inference, its own headless API surface is thinner than ComfyUI's (which already has a well-known raw API); a self-hosted product could either call SwarmUI's own API layer (simpler, has queue/backend management) or bypass it and drive ComfyUI directly — worth a technical spike before committing.
- MIT license plus active, frequent commits (daily) makes SwarmUI the lowest-legal-risk and lowest-staleness-risk option among the four for embedding in a commercial backend.
- Lack of any disclosed company/funding behind SwarmUI is a bus-factor risk: if the lead maintainer stops, there is no institutional backstop (unlike InvokeAI's Invoke Inc).

### Gaps
- Could not confirm exact current headcount of active regular contributors (GitHub's contributors API response was capped at 30 entries without pagination follow-up).
- No direct screenshot analysis was performed (image content not fetched); UI-quality assessment relies on secondary reviewer descriptions, not first-hand visual inspection.

## InvokeAI (invoke-ai/InvokeAI)

### Takeaway
InvokeAI is Apache-2.0 licensed (fully commercial-friendly) with the most polished, "studio-grade" UI of the four and a documented OpenAPI/FastAPI REST backend suitable for headless use, but it is backed by a for-profit company (Invoke Inc.) that sells a separate paid "Professional Edition," and its Wan 2.2 video support is brand-new/prototype-quality as of the versions checked.

### Cited Findings
- Repo: [github.com/invoke-ai/InvokeAI](https://github.com/invoke-ai/InvokeAI) — 28,281 stars, 2,981 forks, 362 open issues (live `gh api` pull, 2026-09-24) — by far the largest and most-starred of the four.
- License: **Apache License 2.0** (SPDX `Apache-2.0`), confirmed both via repo metadata and by fetching the LICENSE file directly ("Apache License / Version 2.0, January 2004"). Apache-2.0 is permissive, commercially reusable, and imposes no copyleft/share-alike obligation — safe for a company to self-host and resell. — [repo metadata](https://github.com/invoke-ai/InvokeAI), [LICENSE file](https://github.com/invoke-ai/InvokeAI/blob/main/LICENSE)
- Last commit: 2026-09-24T02:33:55Z ("feat(krea2): training-free style reference"), with multiple substantive feature/fix commits per day in the preceding week (FLUX.2 fixes, Qwen VRAM fixes, canvas hotkey fixes) — very active, highest commit velocity observed among the four. — [commits API](https://github.com/invoke-ai/InvokeAI/commits)
- Company/edition split: InvokeAI ships a free **Community Edition** ("commercially-friendly license," local/self-hosted/self-managed) and a paid **Professional Edition** (monthly subscription, cloud-hosted/fully managed, adds multi-user support and model training). The GitHub repo description itself states InvokeAI "serves as the foundation for multiple commercial products." — [GitHub repo description](https://github.com/invoke-ai/InvokeAI), pricing referenced at invoke.com/pricing (not independently fetched in this pass)
- Funding: Invoke AI, Inc. (Atlanta, GA) raised a **$3.75M seed round** led by Storm Ventures with SignalFire and Universe Software participating; founded by Kent Keirsey. This is a real, funded company behind the open-source project, which is a maintainer-risk positive (institutional backing) but also the source of a parallel commercial product that competes with third-party resellers. — [FinSMEs seed announcement](https://www.finsmes.com/2023/09/invoke-ai-raises-3-75m-in-seed-funding.html)
- Tech stack: Python backend (12.6M+ bytes, FastAPI-based) with a TypeScript/React frontend (9.4M+ bytes) — a clean, modern web-app stack, not a Gradio wrapper. — [languages API](https://github.com/invoke-ai/InvokeAI/languages)
- API: InvokeAI exposes a REST API at `/api/v1/...` with interactive OpenAPI docs served at `/docs`; the web UI itself is a client of this same HTTP API (built with FastAPI + Socket.IO), and the project can run as a headless REST server with no GUI, including its unified canvas, regional prompting, and built-in queue manager all reachable via API. The frontend's TypeScript types are auto-generated from the OpenAPI schema (`openapi-typescript`), evidencing a real API-first architecture rather than a bolted-on API. — [InvokeAI API dev guide](https://invoke.ai/development/guides/api-development/), [DeepWiki API integration](https://deepwiki.com/invoke-ai/InvokeAI/2.2-api-integration)
- Wan 2.2 video: InvokeAI added Wan 2.2 video generation (text-to-video, image-to-video, and image-to-image-video/interpolation) via its workflow editor, with template workflows to chain/concatenate generated clips into longer sequences. However, InvokeAI's own documentation flags this as a **prototype feature**: "workflows, node fields, and starter-model packaging may change between releases," and the underlying models have "rough edges in coherence and artifacts at longer durations." — [InvokeAI Video Generation feature page](https://invoke.ai/features/video-generation/), [GitHub issue #8459](https://github.com/invoke-ai/InvokeAI/issues/8459)
- Modern image models: version 6.12.0 (March 2026) added FLUX.2 Klein LoRA support, alongside existing SDXL/FLUX/Qwen support referenced across release notes; InvokeAI continues to track new architectures closely (krea2, FLUX.2 fixes appear in the most recent commits above). — [offlinecreator.com InvokeAI overview](https://offlinecreator.com/tool/invokeai)
- UI quality: consistently described by third-party reviewers as "the most refined of any local Stable Diffusion frontend," built around a "Unified Canvas" — a non-destructive, Photoshop-style layered editing workspace with persistent layers, in contrast to ComfyUI's raw node graph. This is the closest of the four to a genuine "studio product" aesthetic. — [PromptQuorum InvokeAI review](https://www.promptquorum.com/power-local-llm/invokeai-review), [offlinecreator InvokeAI vs ComfyUI](https://offlinecreator.com/compare/invokeai-vs-comfyui)
- Maintainer risk: GitHub lists 30+ contributors (API-capped); combined with funded-company backing (Invoke Inc.) and the highest commit cadence of the four, InvokeAI has the lowest single-point-of-failure/bus-factor risk of the four projects. — [contributors API](https://github.com/invoke-ai/InvokeAI/contributors)

### Inferences
- The Apache-2.0 license on the open-source repo means a company can legally self-host and resell InvokeAI-based generation without paying Invoke Inc., but doing so puts the reseller in direct competition with Invoke Inc.'s own "Professional Edition" cloud product — a business/positioning risk distinct from the license itself, worth flagging even though it's not a legal blocker.
- Because video generation is explicitly marked prototype/unstable by InvokeAI's own team, relying on InvokeAI for Wan 2.2 in a production product carries near-term breaking-change risk (node/workflow API surface may shift between releases).
- InvokeAI's API-first architecture (OpenAPI-documented, typed client generation) suggests the cleanest headless integration of the four if the priority is swapping in a fully custom frontend against a stable, documented backend.

### Gaps
- Did not independently fetch invoke.com/pricing to confirm current Professional Edition pricing or exact terms of the "commercially-friendly" Community Edition license language (the phrase is sourced from secondary aggregator text, not Invoke's own licensing page); the underlying repo LICENSE file is confirmed as Apache-2.0, but any *additional* terms InvokeAn/Invoke Inc. might attach to trademarked "Invoke" branding, hosted model packages, or the Professional Edition service itself were not verified from a primary source.
- No first-hand screenshot review was done; UI-quality claims rely on third-party review sites, not direct visual inspection.

## Fooocus and Fooocus-style forks (lllyasviel/Fooocus, mashb1t/Fooocus, SimpleSDXL)

### Takeaway
Fooocus and its direct forks are GPL-3.0 licensed, effectively frozen/EOL for new model architectures (SDXL-only, explicitly will never add FLUX or newer models), have no video generation capability at all, and are not viable candidates for a Wan 2.2-capable product — they should be flagged as non-candidates.

### Cited Findings
- Repo (upstream): [github.com/lllyasviel/Fooocus](https://github.com/lllyasviel/Fooocus) — 53,158 stars, 8,614 forks, 314 open issues (live `gh api` pull, 2026-09-24) — the most-starred single repo of the four projects, but star count reflects historical popularity, not current activity.
- License: **GPL-3.0** (SPDX `GPL-3.0`, "GNU General Public License v3.0") on both `lllyasviel/Fooocus` and the `mashb1t/Fooocus` fork. GPL-3.0 is a strong copyleft license: if a company modifies and distributes/hosts a derivative as a product, GPL-3.0's copyleft terms (and the fact that network use via a hosted SaaS does *not* trigger GPL's source-disclosure requirement, unlike AGPL) mean the company would not be forced to publish its own modifications merely by hosting it as a service — but bundling/distributing modified Fooocus binaries to customers would require releasing source under GPL-3.0 too. This is a **GPL, not AGPL** license — important distinction: hosting-only use (SaaS) does not trigger GPL's copyleft obligations, whereas AGPL would. — [Fooocus repo license field](https://github.com/lllyasviel/Fooocus), [mashb1t fork license field](https://github.com/mashb1t/Fooocus)
- Last commit (upstream lllyasviel/Fooocus): 2025-09-02T20:28:40Z, a CI action version bump only; the last substantive commits were readme/doc updates from January 2025. — [commits API](https://github.com/lllyasviel/Fooocus/commits)
- Last commit (mashb1t/Fooocus fork): most recent real commit is 2025-01-24T15:23:09Z ("fix: change code owner from @lllyasviel to @mashb1t"); `pushed_at` metadata shows 2025-10-28, but that appears to reflect a non-commit push (tag/branch/workflow) rather than new commits, since the commit log shows no entries after January 2025. — [mashb1t commits API](https://github.com/mashb1t/Fooocus/commits)
- Project status: Fooocus's own README declares the project is in "a state of limited long-term support (LTS) with bug fixes only," with explicit statements that there are "no plans to support newer architectures like FLUX." The last tagged release was v2.5.5 (August 12, 2024). — [localaimaster Fooocus guide](https://localaimaster.com/blog/fooocus-guide), [GitHub Discussion #3840 "Fooocus discontinued?"](https://github.com/lllyasviel/Fooocus/discussions/3840)
- Model/video support: Fooocus supports **SDXL only** — "no Flux, no SD3, and no newer architectures" — and has **no video generation capability**. The official project explicitly points users wanting FLUX or video to other tools: Forge, ComfyUI, SwarmUI, or community forks like RuinedFooocus. — [offlinecreator Fooocus vs RuinedFooocus comparison](https://offlinecreator.com/compare/fooocus-vs-ruinedfooocus)
- API/headless: Fooocus historically ships a much more limited API/queue surface than SwarmUI or InvokeAI (a simple Gradio-based UI with some programmatic entry points), consistent with its design goal of being the "simplest" one-click local SDXL tool rather than an integration platform — no OpenAPI/REST documentation comparable to InvokeAI's or SwarmUI's was found.
- SimpleSDXL fork: the actively-referenced Fooocus-style fork "for Chinese and Cloud" use is `metercai/SimpleSDXL` — 872 stars, 40 forks, GPL-3.0 licensed, but its `pushed_at` is 2025-09-03, over a year old relative to this research date, indicating it is also largely stale. (Note: a same-named but unrelated `haoningwu3639/SimpleSDXL` repo exists — a from-scratch SDXL PyTorch reimplementation with only 19 stars — and should not be confused with the Fooocus-derived `metercai/SimpleSDXL`.) — [metercai/SimpleSDXL repo metadata](https://github.com/metercai/SimpleSDXL)
- Tech stack: Python-dominant (2M+ bytes) with a thin JS/CSS layer — consistent with its Gradio-based UI foundation. — [Fooocus languages API](https://github.com/lllyasviel/Fooocus/languages)
- UI quality: minimalist, consumer-friendly one-page Gradio interface — often praised as "the easiest way to generate SDXL images" for non-technical users, but visually and architecturally a basic dev-tool-style Gradio app, not a studio-grade product UI.

### Inferences
- Because Fooocus is architecturally frozen at SDXL and has zero video capability, and its most notable forks are similarly stale (mashb1t inactive since Jan 2025, SimpleSDXL inactive since Sept 2025), none of the Fooocus family can meet the hard Wan 2.2 requirement — this entire family should be excluded from the shortlist regardless of licensing.
- Even setting aside video, GPL-3.0 (not AGPL) means a pure hosted-SaaS use would not legally compel source disclosure, but the stale codebase and lack of a real API make it a poor technical fit independent of licensing.

### Gaps
- Did not exhaustively survey the entire Fooocus fork ecosystem (dozens of forks exist on GitHub); only the two forks named in the assignment (mashb1t, SimpleSDXL) were checked directly. It's possible other more active forks (e.g., RuinedFooocus, mentioned by a reviewer as actively adding FLUX/video) exist but were out of scope for this pass — RuinedFooocus is flagged here only as a third-party mention, not independently verified via `gh api`.
- No direct confirmation of Fooocus's exact API/queue surface from primary source docs (no equivalent to SwarmUI's `docs/API.md` or InvokeAI's OpenAPI docs was located); this claim rests on general project positioning rather than a fetched API reference.

## SD.Next (vladmandic/sdnext)

### Takeaway
SD.Next is Apache-2.0 licensed, actively maintained (commits within days, near-daily changelog updates), already supports Wan 2.2 (5B and 14B/A14B variants) plus FLUX/Qwen-Image, and offers an Automatic1111-compatible API for straightforward headless use — a strong technical/licensing candidate, but it is effectively a single-maintainer (vladmandic) project with no disclosed company or funding backing, and its UI is explicitly a Gradio-based "advanced users" tool, not a studio-polished product.

### Cited Findings
- Repo: [github.com/vladmandic/sdnext](https://github.com/vladmandic/sdnext) — 7,346 stars, 583 forks, 60 open issues (live `gh api` pull, 2026-09-24).
- License: **Apache License 2.0** (SPDX `Apache-2.0`) — permissive, commercially reusable, no copyleft obligations. — [repo license field](https://github.com/vladmandic/sdnext)
- Last commit: 2026-09-21T14:41:50Z ("update changelog"), with recent merges including "feat/qwen-image-2.1" — active development with regular changelog discipline (dated release-discussion threads on GitHub). — [commits API](https://github.com/vladmandic/sdnext/commits), [CHANGELOG wiki](https://github.com/vladmandic/sdnext/wiki/CHANGELOG)
- Description: "SD.Next: All-in-one WebUI for AI generative image and video creation, captioning and processing" — positions itself explicitly as covering both image and video, unlike Fooocus/InvokeAI's image-first framing. — [GitHub repo](https://github.com/vladmandic/sdnext)
- Tech stack: heavily Python (14.7M+ bytes), a fork/descendant of AUTOMATIC1111's stable-diffusion-webui codebase sharing much of the same architecture (Gradio-based UI), with modest CSS/TypeScript/JS for UI polish. — [languages API](https://github.com/vladmandic/sdnext/languages)
- Wan 2.2 video: SD.Next supports Wan 2.2 in both **5B** and **A14B** variants for both text-to-video and image-to-video, exposed through a dedicated Video tab with a generic model-variant selector; supports the optional second-stage low-noise refinement pass (disabled by default, ~54GB additional weights) and standard features like quantization/offloading/TAESD. — [SD.Next Video wiki](https://github.com/vladmandic/sdnext/wiki/Video), [SD.Next Discussion #4482 on Wan 2.2 5B I2V](https://github.com/vladmandic/sdnext/discussions/4482)
- API: SD.Next's backend is "fully compatible with most existing functionality and extensions written for A1111 SDWebUI," including its REST API (with some parameter-naming differences, e.g., sampler/scheduler split). It documents a headless mode explicitly intended "to allow integration into existing content management systems," plus built-in batch processing, API endpoints, webhook notifications, and cloud-storage integration. — [SD.Next API wiki](https://github.com/vladmandic/sdnext/wiki/API), [brightcoding.dev SD.Next overview](https://www.blog.brightcoding.dev/2026/07/16/sdnext-the-revolutionary-ai-media-studio-every-creator-needs)
- Modern image models: model support wiki confirms broad coverage of current open models; the recent commit history explicitly shows "Qwen-Image-2.1" feature work merged September 21, 2026, and FLUX support has been present for some time per general documentation. — [Model Support wiki](https://github.com/vladmandic/sdnext/wiki/Model-Support), [commits API](https://github.com/vladmandic/sdnext/commits)
- UI quality: SD.Next is a Gradio-based WebUI descended from AUTOMATIC1111, targeted at "advanced users" — a utilitarian, tab-and-panel technical interface, not a modern SaaS-studio design; no evidence found of a redesigned or "studio" aesthetic comparable to InvokeAI's canvas or SwarmUI's simplified Generate tab. — [stable-diffusion-art SD.Next install guide](https://stable-diffusion-art.com/sd-next/)
- Maintainer risk: the project is led essentially by a single maintainer, Vladimir Mandic ("vladmandic"), who has publicly stated in a GitHub Discussion that he does not want the project to rely solely on himself and would like additional maintainers with full admin rights — a direct, primary-source acknowledgment of bus-factor risk. No corporate backing or funding was found. GitHub lists 30+ contributors (API-capped). — [SD.Next Discussion #1246 "Initiatives"](https://github.com/vladmandic/sdnext/discussions/1246), [contributors API](https://github.com/vladmandic/sdnext/contributors)

### Inferences
- SD.Next's A1111-API compatibility is a double-edged sword for headless use: it's a well-known, widely-documented API shape (many existing client libraries target it), but the naming/parameter quirks noted above (sampler/scheduler split) mean a drop-in "OpenAI-style clean REST API" experience shouldn't be assumed — expect some adaptation work.
- The explicit single-maintainer bus-factor risk (acknowledged by the maintainer himself) is comparable to or slightly worse than SwarmUI's, and meaningfully worse than InvokeAI's funded-company backing — this should weigh against SD.Next if maintainer continuity is a hard requirement, despite its strong technical/license fit.

### Gaps
- Did not verify whether SD.Next has gained additional co-maintainers since the "Initiatives" discussion was posted (undated in the search snippet); current maintainer-count status as of September 2026 is not confirmed beyond the contributors list.
- No first-hand screenshot review was performed; UI-quality characterization relies on secondary descriptions ("advanced users," Gradio-based) rather than direct visual inspection of current-version screenshots.

## Cross-Cutting Notes (not tied to a single project)

### Takeaway
Of the four candidates, only SwarmUI, InvokeAI, and SD.Next currently meet the hard Wan 2.2 requirement; Fooocus and its checked forks are out. All three viable candidates use permissive licenses (MIT or Apache-2.0) with no AGPL/GPL copyleft concerns for a hosted-SaaS resale model — the one GPL-3.0 project in the set (Fooocus family) is also disqualified on the video-support requirement, so license risk and capability risk happen to point the same direction here.

### Cited Findings
- License summary table (from live `gh api` license fields, 2026-09-24): SwarmUI = MIT; InvokeAI = Apache-2.0; SD.Next = Apache-2.0; Fooocus (upstream and mashb1t fork) = GPL-3.0; SimpleSDXL (metercai fork) = GPL-3.0. **None of the five repos checked are AGPL.** — [SwarmUI](https://github.com/mcmonkeyprojects/SwarmUI), [InvokeAI](https://github.com/invoke-ai/InvokeAI), [sdnext](https://github.com/vladmandic/sdnext), [Fooocus](https://github.com/lllyasviel/Fooocus), [mashb1t/Fooocus](https://github.com/mashb1t/Fooocus), [metercai/SimpleSDXL](https://github.com/metercai/SimpleSDXL)
- Star counts (2026-09-24, `gh api`): Fooocus 53,158 · InvokeAI 28,281 · SD.Next 7,346 · SwarmUI 4,597 · SimpleSDXL fork 872 · mashb1t/Fooocus fork 353. Star count is a lagging/historical-popularity signal and, per the Fooocus finding above, is not a reliable proxy for current suitability — Fooocus has by far the most stars but is functionally frozen and lacks video support entirely.

### Inferences
- Star count should be weighted low relative to recent-commit-date and feature-support evidence when scoring these candidates, since the highest-starred project in this set (Fooocus) is the clearest non-candidate.
- The three viable candidates (SwarmUI, InvokeAI, SD.Next) all share one structural weakness relative to a commercial product bet: none has more than a handful of core maintainers with clear succession plans, and only InvokeAI has real funded-company backing (Invoke Inc., $3.75M seed) — worth factoring into a build-vs-buy-vs-fork risk discussion.

### Gaps
- Reddit r/StableDiffusion 2025-2026 comparison threads were not directly searched/fetched in this pass (time/tool-call budget was prioritized toward primary GitHub sources and official docs); a dedicated pass through r/StableDiffusion could surface additional practitioner sentiment on UI polish and real-world Wan 2.2 performance that wasn't captured here.
