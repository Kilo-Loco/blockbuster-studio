# ComfyUI backend, SwarmUI shell, custom skin

The clearest path to a self-hostable Higgsfield-style studio is **headless ComfyUI as the generation engine, driven through its classic `/prompt`+`/ws` API, wrapped by a thin custom frontend rather than any existing consumer UI** — with SwarmUI's MIT-licensed API layer as a fallback accelerant if a queue/backend-manager is needed faster than building one. ComfyUI itself is GPL-3.0 but that copyleft never triggers for a pure network-hosted SaaS (only AGPL does), it has official native Wan 2.2 workflows plus FLUX/SDXL/Qwen-Image support, and its API is stable, documented, and unauthenticated by design (auth must be added via reverse proxy). The two most tempting shortcuts — Wan2GP for the video engine and ViewComfy for the studio frontend — are both disqualified on licensing grounds for a paid hosted product: Wan2GP's custom license explicitly forbids paid API/SaaS access, and ViewComfy is AGPL-3.0, which does trigger on network use. No existing "Higgsfield clone" frontend both looks the part and actually drives a self-hosted ComfyUI backend, so UI work cannot be fully outsourced to an open-source project — it must be built, using ComfyUI's API-format JSON workflows as the execution contract.

## ComfyUI is the only backend with unambiguous commercial license clearance

ComfyUI core is **GPL-3.0**, transferred from `comfyanonymous` to the `Comfy-Org` organization in January 2026 specifically to de-risk single-account dependency, with near-daily commits and weekly releases as of v0.37.0 (Sept 2026) ([Comfy Org blog](https://blog.comfy.org/p/comfyui-repo-will-moved-to-comfy), [GitHub API](https://github.com/Comfy-Org/ComfyUI)). The critical distinction the notes establish repeatedly: **GPL, unlike AGPL, does not trigger on network/SaaS use** — a company can run ComfyUI as an internal backend that customers only ever touch over HTTP without any obligation to publish source, so long as the code itself isn't distributed to customers. This clears ComfyUI, ComfyUI-Manager (also GPL-3.0), and the Fooocus family (GPL-3.0, but disqualified anyway — frozen at SDXL, zero video, last substantive commit January 2025) for hosted use. Model weights carry separate licenses: **FLUX.1-dev is non-commercial for hosted services** and must be excluded; SDXL (CreativeML OpenRAIL++-M) and the original Apache-2.0 Qwen-Image release are commercially safe, while Qwen-Image-2.1 reversed to a "commercial-blocking research license" ([ByteIota](https://byteiota.com/qwen-image-2-1-open-weights-come-with-a-license-trap/)). Wan 2.2 itself is reported as free/commercial-friendly, though the notes flag this as secondary-sourced and recommend verifying the Hugging Face model card directly before relying on it legally.

By contrast, **Wan2GP (deepbeepmeep/Wan2GP)** — the most tempting "just use this for video" shortcut given 9,580 stars and daily commits — ships under a custom **"WanGP Community License 2.0"** that explicitly names the exact use case at hand as prohibited: "You may not sell WanGP itself, white-label it, embed it in a paid product, or offer paid API / SaaS / hosted / OEM access to it without a separate written reseller or commercial license" ([LICENSE.txt](https://raw.githubusercontent.com/deepbeepmeep/Wan2GP/main/LICENSE.txt)). The license text specifically calls out "API and headless interfaces" and "UI and queueing layers" as covered, foreclosing the "we just host it, we don't sell the software" argument. Wan2GP also carries real maintainer concentration risk — one person holds 1,347 of the project's commits against 309 for the next-highest contributor, with a 1,169-issue open backlog. It remains useful only as a *reference implementation* for VRAM-management technique, or if a commercial license is separately negotiated with the maintainer (contact found: deepbeepmeep@yahoo.com).

## SwarmUI and InvokeAI are the only viable pre-built "shells," but neither matches the target aesthetic

Among general-purpose UIs, only **SwarmUI**, **InvokeAI**, and **SD.Next** clear both the license and Wan-2.2-support bars — all three are permissively licensed (MIT, Apache-2.0, Apache-2.0 respectively) with active commit cadence within days of the research date. **SwarmUI** (4,597 stars, MIT, C#/.NET backend wrapping ComfyUI as its execution engine) has full Wan 2.2 text/image-to-video support and a documented `docs/API.md` REST+WebSocket surface, but it is effectively a single-maintainer project with no institutional backing, and its UI is a "power-tool" dual-mode interface (simple Generate tab + raw node graph), not a from-scratch consumer design ([SwarmUI docs](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/API.md)). **InvokeAI** (28,281 stars, Apache-2.0, FastAPI+React, backed by a funded company — Invoke Inc., $3.75M seed) has by far the most polished, studio-grade UI of any candidate (a Photoshop-style "Unified Canvas") and the cleanest API-first architecture (OpenAPI-documented, typed client generation), but its own docs mark Wan 2.2 video support as an explicit **prototype**, warning that "workflows, node fields, and starter-model packaging may change between releases" ([InvokeAI Video Generation](https://invoke.ai/features/video-generation/)). Building a product on a maintainer-declared-unstable feature is a real roadmap risk. **SD.Next** (7,346 stars, Apache-2.0) supports Wan 2.2 in both 5B and A14B variants via an A1111-compatible API, but its UI is explicitly aimed at "advanced users," it's led by a single maintainer who has publicly asked for co-maintainers to reduce bus-factor risk, and A1111-API compatibility brings naming quirks that require adaptation work rather than a clean integration.

None of these three is a drop-in Higgsfield-style consumer UI. The dedicated "studio frontend" candidates researched specifically to close that gap — **ViewComfy**, **Comfy Deploy**, **Open-Higgsfield-AI**, **OpenCanvas** — each fail on a different axis. ViewComfy (668 stars, Next.js/React, connects to ComfyUI via drop-in `workflow_api.json`) has the most complete "wrap a workflow in a nice app" feature set but is **AGPL-3.0**, which unlike GPL *does* trigger source-disclosure obligations for network-hosted services — a real legal exposure for a paid product, absent a separate commercial license from ViewComfy (none confirmed to exist). Comfy Deploy (YC-backed, GPL-3.0) is developer/ops infrastructure for workflow versioning and deployment, not a consumer-facing creative UI — it would still need a UI layered on top. Open-Higgsfield-AI (600 stars, MIT, visually the closest to the target aesthetic per its own screenshots) doesn't use ComfyUI at all — it calls the third-party paid Muapi.ai gateway, meaning its generation layer would need a full rewrite to hit a self-hosted backend even though its MIT license and UI shell are reusable in principle. OpenCanvas (40 stars) is too early-stage to be a serious base.

## Comfy Org's own App Mode is the only first-party, fully self-hostable "studio" layer

A newer option surfaced directly from Comfy Org itself: **App Mode / App Builder**, shipped into the official `Comfy-Org/ComfyUI_frontend` in 2026 (front-end v1.41.13+), which lets a workflow author expose a simplified input/output interface — prompt box, image upload, model picker, output preview — without the node graph, shareable via a single URL ([Comfy Org blog](https://blog.comfy.org/p/from-workflow-to-app-introducing)). It inherits ComfyUI core's GPL-3.0 license (same clearance logic as the backend) and requires zero new integration risk since it's literally the frontend already running. However, its companion marketplace layer, **ComfyHub**, is a Comfy Org–hosted preview service (application-gated publishing), not something to self-host as a branded product — App Mode alone, without ComfyHub, is the reusable piece, and even App Mode is still visually a ComfyUI-family interface, not an SaaS-studio redesign at the polish level of Higgsfield or InvokeAI's canvas.

## The ComfyUI API surface is stable, documented, and exactly what a custom frontend needs

The classic route table — confirmed live in `server.py` against the current v0.37.0 tag — is unchanged in shape from long-standing tutorials: `POST /prompt` (submits API-format workflow JSON to the execution queue, returns a `prompt_id`), `GET /ws` (WebSocket delivering `status`/`execution_start`/`executing`/`progress`/`executed` events), `GET /view` (retrieves output files by filename/subfolder/type), `POST /upload/image` and `/upload/mask` (input uploads), `GET /history` and `/history/{prompt_id}` (job records), and `GET /object_info` (full node-schema introspection) — all documented at [docs.comfy.org](https://docs.comfy.org/development/comfyui-server/comms_routes). Comfy-Org has additively layered a more REST-conventional `/api/jobs` family (filter/sort/paginate, cancel) on the same queue, and operates a separate hosted **Comfy Cloud** product (cloud.comfy.org) with its own Router/API-key model — but that is an alternative to self-hosting, not a replacement for the classic API, and its docs reference URL 404'd during this research, so its details remain unverified. Two operational facts matter most for a single-Runpod-GPU deployment: ComfyUI has **zero built-in authentication** (a reverse proxy with API-key/Bearer enforcement is mandatory in production, or community nodes like `ComfyUI-Login`), and it is **single-process, single-job-at-a-time** with no built-in multi-GPU scheduler — the documented production pattern is one ComfyUI process per GPU behind an external queue, which matches a one-Runpod-GPU deployment naturally since true parallelism isn't available on one GPU anyway. A RAM-leak issue on repeated batch workflows was reported and closed (GitHub #11301) but without a confirmed resolving commit, so long-running video/batch-heavy workers should still budget for periodic restarts.

## Recommended architecture

Run **headless ComfyUI** (`--listen`, no browser launch) as the sole generation engine on the Runpod GPU, behind a reverse proxy (Caddy/Nginx) that adds API-key auth and rate limiting, since ComfyUI provides neither. Use **SDXL or Apache-2.0 Qwen-Image** (not FLUX.1-dev, not Qwen-Image-2.1) as the image model and the **official native Wan 2.2 workflows** (5B for lower VRAM, 14B for quality, with sequential/offloaded loading to share one GPU) for video — both have first-party Comfy Org example workflows, not just community hacks. Do **not** adopt Wan2GP or ViewComfy as-is given their license terms explicitly blocking or complicating paid hosting; Wan2GP's VRAM-offload techniques and node-graph shape are worth studying as reference, not shipping. Build a **thin custom frontend** (Next.js/React, similar stack to what ViewComfy and Open-Higgsfield-AI already demonstrate is sufficient) that submits API-format JSON to `/prompt`, tracks progress over `/ws`, and renders outputs from `/view` — this is the only path to genuine Higgsfield-level visual polish, since no existing project combines that polish with a self-hosted ComfyUI backend under a commercially clean license. If engineering time is the binding constraint rather than design polish, SwarmUI (MIT, already wraps ComfyUI, has a working API and queue manager) is the fastest-to-ship fallback, accepting its "power tool" look as a starting skin to reskin later rather than the final product.
