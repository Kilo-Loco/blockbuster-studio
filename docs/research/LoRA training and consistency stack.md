# Wan 2.2 and Z-Image LoRA stack for a 4090

For a self-hosted ComfyUI filmmaking app on a single RTX 4090 (24GB), **ostris/ai-toolkit (MIT) is the best headless training backend**, **Kijai's dual-expert LoraLoaderModelOnly pattern plus the dedicated ZImageTurboLoraLoader node is the correct runtime path**, and **Qwen-Image-Edit-2509/2511 combined with Wan-native VACE (Reference-Anything) is the strongest zero-shot consistency layer** — with per-character LoRA training reserved for users who want maximum fidelity at scale. All three legs run comfortably within 24GB using fp8/quantization, and all are Apache-2.0/MIT-licensed with the exception of AGPL SimpleTuner and a few FLUX-ecosystem consistency tools carrying non-commercial licenses. The single biggest gap across all three research areas is the near-total absence of primary-source, reproducible wall-clock/VRAM benchmarks for small (~20-image) LoRA training runs and for several consistency methods — those numbers should be treated as estimates until validated with real training jobs on the target hardware.

## Training tools: ai-toolkit and diffusion-pipe cover the full model set

Only two of the four shortlisted tools have documentation explicitly confirming support for all five target models (Wan 2.2 14B, Wan 2.2 TI2V-5B, Z-Image-Turbo, Qwen-Image, Chroma): **ostris/ai-toolkit** and **tdrussell/diffusion-pipe** ([ai-toolkit](https://github.com/ostris/ai-toolkit), [diffusion-pipe supported_models.md](https://github.com/tdrussell/diffusion-pipe/blob/main/docs/supported_models.md)). musubi-tuner and SimpleTuner support most of the set but lack confirmed TI2V-5B/Chroma coverage in primary docs. OneTrainer should be excluded outright — it has **no Wan 2.x LoRA support**, and the maintainer has deprioritized it ([Issue #709](https://github.com/Nerogar/OneTrainer/issues/709)).

| Tool | License | Confirmed models | Headless CLI | Built-in captioning | Activity (Sep 2026) |
|---|---|---|---|---|---|
| ai-toolkit | MIT | All 5 | Yes (`run.py config.yml`), optional UI | Florence-2/Janus Pro + newer Qwen-3-VL captioner | 12.1k stars, 1,574 commits |
| musubi-tuner | Apache-2.0 | Wan 14B, Qwen-Image, Z-Image (TI2V-5B/Chroma unconfirmed) | Yes, CLI-only | Built-in Qwen-VL script | 2.1k stars, updated Sep 16 2026 |
| diffusion-pipe | GPL-3.0 | All 5 | Yes, CLI-only, no UI | None (external captioning required) | ~2k stars, updated Aug 8 2026 |
| SimpleTuner | AGPL-3.0 | Wan, Z-Image, Qwen-Image, Chroma (TI2V-5B unconfirmed) | Yes, CLI + optional UI | "CaptionFlow" (internals unconfirmed) | 2.9k stars, 10,710 commits |

For a **commercial hosted product**, license matters: ai-toolkit (MIT) and musubi-tuner (Apache-2.0) carry the least friction; SimpleTuner's AGPL-3.0 network-use clause is a real legal consideration for a paid SaaS backend and should get a lawyer's review before adoption ([bghira/SimpleTuner](https://github.com/bghira/SimpleTuner)). No tool in this set was confirmed to expose a documented, versioned REST API — all four are driven via CLI + config file, which is actually the simpler integration target for a Runpod job-queue wrapper ([ai-toolkit](https://github.com/ostris/ai-toolkit), [diffusion-pipe](https://github.com/tdrussell/diffusion-pipe)). **Flagged as unverified/conflicting**: no primary-source benchmark exists for a 20-image character LoRA's wall-clock time on a stock 4090 — one secondary source claims "under 10 minutes," another claims "4-10 hours" for 200-400 images at 2000-3000 steps ([Apatero](https://www.apatero.com/blog/wan-22-video-lora-training-time-complete-analysis-2025)); these disagree by an order of magnitude and neither is authoritative. Treat 1-4 hours for Wan 2.2 14B and under 1-2 hours for Z-Image-Turbo as a researcher estimate only, pending an actual test run.

## ComfyUI LoRA loading requires per-expert wiring and dedicated Z-Image nodes

Wan 2.2 14B's MoE architecture splits into high-noise and low-noise expert checkpoints that must be treated as **separate model graphs**; LoRAs are applied per-expert via `LoraLoaderModelOnly` (not the standard `LoraLoader`, which improperly touches CLIP conditioning), each feeding its own `ModelSamplingSD3` → `KSampler` chain ([docs.comfy.org Wan2.2 tutorial](https://docs.comfy.org/tutorials/video/wan/wan2_2); [Civitai: WAN 2.2 High and Low](https://civitai.com/articles/18460/wan-22-high-and-low-or-how-to-add-new-loras-in-comfyui-with-wan-22)). Community consensus (not officially documented by Comfy Org) is to keep the high-noise pass free of character LoRAs, since it dominates composition, and to apply acceleration LoRAs like LightX2V mainly on the low-noise pass at 0.4-0.6 strength ([RunComfy: Kijai Wrapper Low VRAM workflow](https://www.runcomfy.com/comfyui-workflows/wan-2-2-low-vram-kijai-wrapper-comfyui-video-generation)). Multiple LoRAs chain natively in ComfyUI, but stacking beyond 2-3 at full strength causes oversaturation; combined strength under ~1.5 and per-LoRA sliders are the recommended UX pattern ([Easton Dev](https://eastondev.com/blog/en/posts/ai/20260720-comfyui-lora-guide/)) — again community guidance, not vendor-documented.

Z-Image-Turbo is LoRA-compatible but **not via ComfyUI's stock loader**: because it stores fused QKV attention weights, the generic loader silently drops LoRA weights rather than erroring. The dedicated `Comfyui-ZiT-Lora-loader` extension (`ZImageTurboLoraLoader`/`ZImageTurboLoraStack`) remaps keys correctly and must be standardized on for any Z-Image LoRA path ([RunComfy: Z-Image Turbo LoRA Loader](https://www.runcomfy.com/comfyui-nodes/Comfyui-ZiT-Lora-loader/z-image-turbo-lora-loader)).

For LoRA discovery/download, **Civitai's REST API** (`GET /api/v1/models`, `/api/v1/model-versions/{id}`, download via `GET /api/download/models/{id}` which redirects to a signed URL) is fully documented at [developer.civitai.com](https://developer.civitai.com/site/reference/models). A documented bug means `nsfw=true/false` does not reliably filter by the finer `nsfwLevel` enum ([Issue #1795](https://github.com/civitai/civitai/issues/1795)), so the app should filter client-side on `nsfwLevel` rather than trust the boolean. **Hugging Face Hub** browsing/downloading uses `huggingface_hub`'s `HfApi.list_models()` and `hf_hub_download()` with token-gated access via `HF_TOKEN` ([HF: Search the Hub](https://huggingface.co/docs/huggingface_hub/main/en/guides/search)); there is no LoRA-specific enumerated endpoint, so filtering relies on Hub tag conventions.

## Zero-shot consistency has strong Wan-native and FLUX-ecosystem options

| MAGREF | Yes | Unconfirmed | ~70GB — does not fit 24GB | Unconfirmed |

VACE and Wan 2.2 Animate are the most defensible picks because both are Wan-native with official ComfyUI nodes and Apache-2.0 licensing ([Comfy.org: Wan Animate](https://blog.comfy.org/p/wan-animate-2-is-now-available-in); [ComfyUI docs: VACE](https://docs.comfy.org/tutorials/video/wan/vace)). Qwen-Image-Edit generates consistent multi-angle reference stills upstream of Wan (character face/outfit and location/scene) without training ([docs.comfy.org: Qwen-Image-Edit-2511](https://docs.comfy.org/tutorials/image/qwen/qwen-image-edit-2511)). **InfiniteYou's CC BY-NC 4.0 model license disqualifies it for commercial use** ([bytedance/InfiniteYou LICENSE](https://github.com/bytedance/InfiniteYou/blob/main/LICENSE)) — flag this prominently. **MAGREF's ~70GB VRAM requirement rules it out entirely** for a 24GB card ([MAGREF-Video/MAGREF](https://github.com/MAGREF-Video/MAGREF)). Several promising methods (Stand-In, ACE++, USO, Lynx) have **no confirmed ComfyUI integration or VRAM figures** and should be prototyped, not assumed production-ready.

## Recommended stack

**(a) Training:** Standardize on **ai-toolkit (MIT)** as the sole training backend. It's the only tool with confirmed support for all five models, built-in captioning (Florence-2/Janus Pro, plus Qwen-3-VL), and both a headless CLI (for the Runpod job queue) and an optional UI (for debugging). Its permissive license removes legal friction entirely. Keep diffusion-pipe as a fallback only if ai-toolkit's quantization ceiling proves insufficient on 4090s in practice — the actual wall-clock number for a 20-image run must be empirically validated, not assumed.

**(b) Runtime LoRA handling:** Wire every Wan 2.2 LoRA through **`LoraLoaderModelOnly` on both high-noise and low-noise expert graphs independently**, defaulting character/style LoRAs to the low-noise pass and keeping the high-noise pass clean; cap simultaneous stacks at 2-3 LoRAs with user-exposed strength sliders (combined ≤1.5). Standardize Z-Image-Turbo LoRA loading exclusively on the **`Comfyui-ZiT-Lora-loader`** extension to avoid the silent-drop failure mode of the stock loader. Build the LoRA browser against **Civitai's documented REST API**, filtering NSFW client-side on `nsfwLevel` rather than the buggy `nsfw` boolean, with **Hugging Face Hub** (`HfApi`/`hf_hub_download`) as the secondary source.

**(c) Zero-shot character + location consistency:** Use **Qwen-Image-Edit-2509/2511** to generate consistent multi-angle reference stills of characters and locations, then hand those stills to **Wan-native VACE (Reference-Anything)** for shot generation and **Wan 2.2 Animate** for motion-driven character animation — all three are open-weight, Apache-2.0-licensed, and natively supported in ComfyUI, avoiding the CC BY-NC licensing trap of InfiniteYou and the VRAM impossibility of MAGREF. This zero-shot path should be the default for most users; per-character LoRA training via ai-toolkit remains the opt-in path for users who need maximum identity fidelity across large shot counts.
